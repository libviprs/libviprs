`sharpen` was never the problem. #581 got re-bisected onto the `scRGB -> sRGB`
store, and this is the fix for it.

## What vips actually does

It does not evaluate the sRGB transfer function per pixel. `calcul_tables`
(`colour/LabQ2sRGB.c:126-146`) builds a `range`-entry integer table once, in
`float`,

```c
Y2v[i] = rintf((range - 1) * srgb_encode((float) i / (range - 1)));
Y2v[range] = Y2v[range - 1];   /* so the interpolator's +1 stays in bounds */
```

and `vips_col_scRGB2sRGB` (`:282-353`) / `vips_col_scRGB2BW` (`:385-428`) then
scale the linear value by `range - 1`, clip it, take the integer part,
interpolate **linearly between two already-rounded integer entries**, and
`rintf` the chord.

Three quantisations. libviprs evaluated `srgb_encode` analytically in `f64` and
rounded once, so it had none of them.

## Where it hurt

Sweeping the neutral LabS L codes (L = 0..32767 at a = b = 0) against vips 8.18.4:

| surface | before | after |
|---|---|---|
| `Labs -> b-w` | 5434 / 32768 | **0** |
| `Labs -> sRGB` | 16295 / 98304 | **0** |
| `Labs -> grey16` | 6115 / 32768 | 38 / 32768 |
| `Labs -> rgb16` | 17936 / 98304 | 123 / 98304 |

and on a 21x21x21 Lab grid:

| surface | before | after |
|---|---|---|
| `b-w` | 2646 / 9261 | **0** |
| `sRGB` | 2965 / 27783 | **0** |
| `grey16` | 1323 / 9261 | **0** |
| `rgb16` | 3223 / 27783 | 25 / 27783 |

Every difference, before and after, is exactly one count.

The 16-bit residue is **not** this mechanism and I did not chase it. vips runs
`Lab2XYZ` and `XYZ2scRGB` in `float`; libviprs runs them in `f64`, and the two
land about 1e-8 apart, which is a fifth of a code at 16-bit range and invisible
at 8. Feeding vips's own `colourspace ... scrgb` output through the ported
lookup still leaves 12 of 27783 on the Lab grid, which is the proof it sits
upstream of the table.

## Two things the C source does not show

**The build fuses the multiply-add.** `(1.0F + 0.055F) * powf(f, 1.0F / 2.4F) -
0.055F` compiles to a single `fmadd` on the arm64 Homebrew 8.18.4, and so does
the interpolation. From the shipped dylib:

```
$ otool -tvV -p _calcul_tables .../libvips.42.dylib
    bl      _powf
    fmadd   s0, s0, s9, s13
    fmul    s0, s0, s11
    frintx  s0, s0
```

That decides **45 of the 65536** entries of the 16-bit table, each by a count.
It decides none of the 256-entry table. I pinned it with `f32::mul_add`, which
is a true FMA everywhere in Rust and therefore does not depend on what the host
optimiser feels like doing. `calcul_tables_matches_the_vips_y2v_tables` pins
seven of the entries it decides.

**`frintx` is ties-to-even.** `rintf` rounds halves to even, not away from zero,
and Rust's `f64::round` does the opposite. The 16-bit path is where that is
visible: the chord lands on an exact `.5` for 70 of the 32768 neutral L codes.
`labs [4746, 0, 0] -> grey16` is 9404 in vips (chord 9404.5, resolving down) and
`labs [5505, 0, 0]` is 10652 (chord 10651.5, resolving up), so the test pins one
tie in each direction and neither `floor` nor `ceil` nor half-away passes both.

## Folded in: the sRGB -> HSV quantiser

This is a second bug and I fixed it here rather than filing it, because the LUT
is what made it visible and my own HSV test could not pass around it. It is five
lines.

`sRGB2HSV.c:113-117` writes the hue and the saturation into an `unsigned char`,
which drops the fraction; libviprs handed them out unrounded and let the writer
round. It stayed hidden because the analytic sRGB encode produced flat greys
where the table produces a real spread, and a flat grey has `delta == 0` and so
no hue or saturation to get wrong. Over a 46176-pixel sRGB grid:

```
round    + f64 ratio  45370 / 138528 codes differ   <- what libviprs did
truncate + f64 ratio    299 / 138528
truncate + f32 ratio      0 / 138528                <- what vips does
```

The hue's ratio is an `f32` division there too (`secondary_diff` is a `float`
and `delta` an `unsigned char` cast to one; only the `42.5 *` promotes back),
which is the other 299.

## One test moved, and it moved onto vips

`convolution::tests::sharpen_sharpens_luminance_only` asserted that sharpening
leaves the a/b chroma codes within a count, on the reasoning that the unsharp
mask only touches L. That premise is false and libvips does not hold to it
either. On the test's own hard edge the mask lifts the bright side to scRGB
values the per-channel lookup quantises to `[249, 249, 248]`, not a flat grey,
which reads back as LabS chroma `[-43, 119]`.

vips 8.18.4 gives byte-identical output on that image, so the test now pins the
measurement instead of the tolerance, and is renamed
`sharpen_sharpens_an_edge_like_vips`. It is strictly stronger: it compares the
whole 20x10 result against vips rather than checking a self-consistency
property.

## Not changed

The `v2Y` half of `calcul_tables`, the sRGB -> linear direction. That stays
analytic in `f64`. vips reads it out of a `float` table, so the two differ by an
`f32` rounding of a linear value, which is orders of magnitude below a code and
not what this issue is about.

CMYK is untouched, despite the issue listing it as one of the five sites. Two
reasons, and I think the site label in the issue is simply off by one arm:
`colour.rs:988` (against the revision the issue was written from) is the **`Hsv`**
arm, not `Cmyk`. The five listed offsets are exactly 86 lines below the Hsv,
Srgb, Rgb16, Bw and Grey16 arms on `a0fa772`, so the set is right and only the
first name is wrong. And CMYK could not have been in scope anyway:
`{ XYZ, CMYK }` is `vips_XYZ2CMYK` alone (`colourspace.c:230`), which never
touches the sRGB lookup, and on this build it is the lcms leg of that file
rather than the naive ink model libviprs ports (`XYZ2CMYK.c:52`, `HAVE_LCMS2`).

Closes #581.
