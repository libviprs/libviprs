Still-image GIF load and save, filling in the `src/gif.rs` stub #563 created.

**This PR is a work in progress.** The tests below are the failing pins, committed first as evidence the gap is real; the implementation follows.

### What is wrong today

`#563` wired GIF into the shared sniff table and routed it to `image`'s `GifDecoder`, and left `Raster::encode_gif` as a typed `Unsupported` stub. Both halves need work.

Load through the facade is close but not parity: `image::codecs::gif::GifDecoder::color_type()` is hard-coded to `Rgba8`, while `vips gifload` emits **3 bands** unless some frame declares a transparent index (`nsgifload.c:271`, `has_transparency ? 4 : 3`, and `:522-534` drops the alpha byte per pixel). The facade also exposes nothing else `gifload` sets: no `n-pages`, no `loop`, no `bits-per-sample`, no palette.

Save has no encoder at all, and `image`'s `GifEncoder` cannot become one: measured on `image` 0.25.10's `codecs/gif.rs`, zero occurrences of "interlac", zero of "dither", and `encode` routes straight to `Frame::from_rgb_speed` / `from_rgba_speed` with no palette control.

### Not changed

Animated GIF is #572 (load) and #573 (save), blocked on the page model (#564) and the `.v` trailer (#565). For a multi-frame input this lane loads **frame 0**, which is exactly `vips gifload`'s own default (`page=0, n=1`), and attaches `n-pages` so a caller can tell an animation from a still.

Descoped from #571: `effort`, `reuse`, `interpalette-maxerror`, `interframe-maxerror`, `keep-duplicate-frames`. Those are cgif-specific palette-reuse and frame-coalescing machinery with no pure-Rust equivalent.
