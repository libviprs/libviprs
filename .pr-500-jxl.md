Still-image JPEG XL: load through `jxl-oxide` and lossless save through `zune-jpegxl`, replacing the typed-`Unsupported` stub, **behind a new non-default `jxl` feature**. Build with `--features jxl` and `.jxl` becomes a live row in the content sniffer, in `Raster::save`'s extension route and in `Raster::encode_to_buffer`'s format route. Animated JXL stays out; it is #621 and it needs the page model in #564.

The feature gate came out of the panel and is written up under **Dependencies** below, with re-measured numbers. Everything in the sections between here and there describes the codec with the feature on.

JPEG XL is the first format in the sniff table with **two unrelated magics**, the bare `FF 0A` codestream and the 12-byte ISOBMFF signature box, and both had to go in or half the format would silently not decode. Both forms appear in the fixtures: `vips jxlsave --lossless --keep none` writes the bare form for an 8-bit image and the boxed form for a 16-bit or float one.

## Decode parity splits by path, and only one of them earns a tolerance

libjxl and `jxl-oxide` both target the JPEG XL conformance suite, so this is a parity port rather than an approximation. Measured on the same 4x3 ramp, both directions:

| path | result |
|---|---|
| lossless modular, 8-bit RGB / RGBA / `b-w` | identity, every channel exact |
| lossless modular, 16-bit RGB | identity at full range, every channel exact |
| lossless modular, float RGB | identity, every dyadic value exact |
| VarDCT (default `jxlsave`) | 7 of 36 channels differ, **all by exactly 1** |

So the lossless pins carry **no tolerance at all** and the VarDCT pin carries exactly one count per channel and no more. A lossless round trip that stops being bit-exact is a bug rather than imprecision, and the test says so.

The other direction as well, which is the half a decode-only suite cannot check: vips reads back what libviprs writes, at the right band count and interpretation. `oracle-captures/foreign-jxl/oracle.json` records `viprs_rgb.jxl` as `4x3 uchar, 3 bands, srgb`, `viprs_rgba.jxl` as `4 bands`, `viprs_grey.jxl` as `1 band, b-w` and `viprs_rgb16.jxl` as `4x3 ushort, 3 bands, rgb16`, with every `vips getpoint` matching the source.

## What the module decides, and why

**The carrier follows the file.** `jxlload.c:679-696` picks float for float samples, 16-bit above 8 declared bits, and 8-bit otherwise, so a 16-bit file comes back `Rgb16` and a float one comes back `FloatF32(3)` tagged `scrgb` rather than being quantised on the way in. The interpretation is tagged explicitly rather than inferred, because JPEG XL's band count and its *colour* channel count are different questions and only the second one decides the tag: a two-band greyscale-plus-alpha file is still `b-w`.

**Greyscale stays one band**, which is where JPEG XL and WebP part company. `webpsave` promotes a `b-w` image to three bands because the format stores no greyscale; `jxlsave` does not, because it does.

**The EXIF box is not the EXIF blob.** JPEG XL stores the TIFF block behind a big-endian 4-byte offset and without the `Exif\0\0` prefix a JPEG APP1 segment carries, so `jxlload.c:630-664` skips the offset and glues the prefix back on. Two hand-built fixtures carry the same TIFF block at offsets 0 and 6 and vips reports the identical 16-byte blob for both, which is what proves the offset is skipped rather than ignored. A JPEG transcoded with `--keep all` comes back with the identical 186-byte blob the JPEG loader attached.

**A malformed EXIF box costs the blob, not the image.** This is a deliberate divergence. vips fails the whole load when the offset runs past the payload (measured: `vipsheader` warns `invalid data in EXIF box`, exits 1 and prints no header). Refusing an otherwise-valid image over a metadata box is the wrong trade for a decoder reading untrusted bytes. The divergence runs the other way for a nonconforming box that already carries the `Exif\0\0` prefix, which vips special-cases and `jxl-oxide` cannot expose, so libviprs drops a blob vips keeps. Both shapes are in the corpus.

**Lossy is unrepresentable rather than ignored**, which is the answer #568 took for WebP. `zune-jpegxl` is a lossless modular encoder with no VarDCT path anywhere in it, so `jxlsave`'s `distance`, `Q`, `tier` and `effort` have nothing behind them and none of them is a field this crate accepts and discards. `Compression` is `#[non_exhaustive]` with one variant, so `Lossy { distance }` can join as a minor bump.

**16-bit encodes**, unlike WebP. There is no narrowing question to answer here: the format and the encoder both hold 16-bit samples. Float is refused with a message naming the remedy, because the encoder does not.

**Two pixels is the floor on each axis**, and it is a libviprs limit rather than a format one. `vips jxlsave` writes an 18-byte 1x1 file happily; `zune-jpegxl`'s `encoder.rs:1059-1064` rejects `width <= 1` or `height <= 1` outright. The refusal names the floor instead of letting the dependency's `ZeroDimension("width")` reach the caller.

**No metadata on save.** The encoder writes a bare codestream with no box container, so there is nowhere for an ICC profile, an EXIF block or an XMP packet to go. `vips jxlsave --keep none` writes the same form, so the shapes agree where they overlap and `--keep all` simply has no encoder behind it. `SaveOptions` therefore has no `keep` field, and `save` and `save_stripped` write byte-identical `.jxl` files, which is pinned rather than left as an accident.

**The orientation is applied, not tagged.** Every pixel accessor `jxl-oxide` exposes applies the header orientation itself, so the raster comes back upright with `orientation` 1, where `jxlload.c:822` tags it and leaves `vips_autorot` to turn the pixels. Only reachable with a third-party file: `jxlsave.c` never sets the field.

**CMYK is refused rather than mislabelled.** libjxl counts a `Black` channel as an extra channel, so `jxlload.c:700-737` switches on three colour channels and tags a CMYK file `srgb` with four bands, which is not what those four bands are. Nothing in this build can produce such a file either: `vips jxlsave` converts a `cmyk` image to sRGB on the way in.

## Limits reach the decoder, in two places

The feed is split in two phases specifically so they can. `max_coord` and `max_pixels` run on the declared header geometry and the allocation budget runs on the frame buffer that geometry implies, all before a byte of frame data is fed in; `jxl-oxide`'s own `AllocTracker` then carries the same number into the decoder as defence in depth. A refusal from either place reports the same typed variant, which needed `jxl-grid` named directly so the tracker's `OutOfMemory` can be told from a corrupt bitstream. The test pins that mapping, so if the two crates ever stop unifying it goes red rather than silently downgrading to "malformed".

## The oracle and the fuzz target

`oracle-captures/foreign-jxl/` records seventeen things measured on the real vips 8.18.4 binary, with `capture.py` regenerating them from deterministic ramps and `commands.sh` listing all 348 commands. `vips --vips-config` reports `JXL load/save with libjxl: true` and `vips -l | grep -i jxl` lists all seven operations, so nothing here is hand-derived. Ten fixtures are small enough (34 to 251 bytes) to embed in the unit tests verbatim.

`fuzz/fuzz_targets/fuzz_jxl.rs` joins `fuzz_decode` and `fuzz_radiance` with a 26-seed corpus, and `cargo test` sweeps that corpus so every seed is a `cargo test` regression rather than something only a fuzz run would notice. This is the format where a fuzz target earns its keep most obviously: `jxl-oxide` is the widest surface the crate points at untrusted bytes, and it has already shipped one advisory of exactly the kind a fuzzer finds.

## Dependencies, and why the feature gate

**The first version of this section counted the wrong thing, and that is what the panel held the PR on.** It said +17 lock entries and it was not wrong about the lock; it was wrong that the lock is what a consumer compiles.

Re-measured on this branch:

| | crates |
|---|---|
| `Cargo.lock`, `origin/main` -> this branch | 260 -> 277, **+17** |
| `cargo tree -p libviprs -e normal`, default build | 115 -> **115, +0** |
| `cargo tree -p libviprs -e normal --features jxl` | 115 -> 136, **+21** |

The 17 and the 21 differ by exactly four: `tracing`, `tracing-core`, `once_cell` and `pin-project-lite` were already in `Cargo.lock` through the `tracing-subscriber` **dev**-dependency, and a dev-dependency of this repo is in nobody else's build. So the lock delta undercounts the real cost by four crates, and one of those four is the important one.

`tracing` arrives as a hard, non-optional dependency of both `jxl-oxide` and `jxl-bitstream`. This crate makes `tracing` opt-in on purpose (`tracing = ["dep:tracing"]`, `default = []`), so an unconditional `jxl-oxide` turned that declaration into a false statement for every consumer, and `default-features = false` could not get it back out, because the JXL crates were unconditional `[dependencies]` entries. Behind `jxl`, `cargo tree -e normal -i tracing` prints "nothing to print" in a default build.

Binary cost, measured on a release example that reaches the whole load and save surface: **2,381,616 -> 4,781,648 bytes, +100.8%**.

The crate had already written the policy for this, two features away in the same manifest: `svg` is non-default because it is the one feature that costs a meaningful number of dependencies, +29 lock entries, and nobody who does not rasterise SVG should pay for the compile. 21 against 29 is the same order, so `jxl` gets the same answer and, deliberately, the same implementation: cfg stubs that keep every signature, and CI jobs so the gated code is still compiled, linted and run.

The 21 are thirteen `jxl-*` crates, `zune-jpegxl`, `brotli-decompressor` and its two `alloc-*` crates for the box decompressor, and `tracing` with its three. `zune-core` and `jxl-grid` are named directly and cost nothing: `image` and `zune-jpeg` already pull the first and `jxl-oxide` already depends on the second, so both are in the graph of a default build with the feature off.

### What the feature does and does not move

Nothing about the public surface. The module, `jxl::SaveOptions`, `jxl::Compression`, `MIN_DIMENSION` and every entry point stay exactly where they are with exactly their signatures; only the bodies move behind the cfg, which is `src/svg.rs`'s shape. Without the feature:

- `decode_jxl` returns the `Unsupported` I/O error `decode_svg` returns without `svg`.
- `encode_jxl`, `save_jxl` and `encode_to_buffer("jxl")` return `EncodeError::Unsupported { format: "jxl" }`, the variant every format with no encoder in the build already returns, so a caller matching on the encode spine learns no new variant.
- `.jxl` leaves `Raster::save`'s extension route entirely and reads as an unsupported extension.
- The **sniff** route still points at `decode_jxl`, on purpose. Falling through to the generic reader would report "these bytes are not an image" for a perfectly good JPEG XL, which is a different and worse answer than "this build has no JPEG XL".

Every unit test carries the cfg and there are new tests on the far side of it, in `src/jxl.rs`, `src/connection.rs`, `src/imageio.rs` and `tests/jxl_ported_surface.rs`, so neither build has an arm nobody compiles.

Zero `-sys` crates, zero `links =` keys, zero `build.rs`, and no `.c`/`.h` anywhere in the added set. `zune-jpegxl` is `#![forbid(unsafe_code)]`. Licences are not uniformly `MIT OR Apache-2.0` as the scoping note assumed: the thirteen `jxl-*` are, `zune-jpegxl` and `zune-core` are `MIT OR Apache-2.0 OR Zlib`, `brotli-decompressor` is `BSD-3-Clause/MIT` and the two `alloc-*` crates are BSD-3-Clause only. Every family already has in-tree precedent.

`jxl-oxide` is floored at **0.12.6** because every release at or below 0.12.5 carries **GHSA-66m8-c62j-h6v5**: `FrameBuffer::new` multiplies `width * height * channels` as unchecked `usize`, so an overflow builds an undersized buffer whose safe grouped accessors then hand out oversized slices.

### The MSRV pin is a floor and not an `=`, deliberately

The scoping note suggested pinning tightly because `jxl-oxide` declares no `rust-version`. Measured, **none of the thirteen `jxl-*` crates declares one**, and `jxl-oxide` requires its siblings by caret, so `=0.12.6` would freeze one crate out of thirteen while `jxl-frame`, `jxl-render` and the rest kept floating. That is the appearance of protection rather than the thing, and it additionally breaks any consumer who separately depends on `jxl-oxide ^0.12.7`, because `=` cannot unify upward.

The hazard is real and it is carried by the gate instead: `Cargo.lock` is not committed here, so CI resolves fresh on every push and runs `cargo +1.97 check --all-targets --features jxl`. A family-wide MSRV bump shows up as a red build within a day rather than in a consumer's lockfile. That feature name is load-bearing now the crates are optional: without it they are not in the graph and the job would have quietly stopped checking the one family it was written for. The whole argument is in `Cargo.toml` next to the pin. The real fix, if a hard freeze is ever wanted, is a committed lockfile.

## Two things the panel found that were wrong on their own

**The save refusal lied.** `SaveError::UnsupportedExtension` read "libviprs encodes png, jpg/jpeg, gif, webp, and v/vips", which stopped being true the moment `.jxl` became a save arm: `save("x.avif")` told the caller JPEG XL was unsupported at the moment it became supported. It could not stay a fixed string once the feature landed either, so the tail now comes from the same set the extension route dispatches on. `save_error_lists_exactly_the_wired_extensions` parses the list back out of a rendered message, saves under every name in it, and checks that the names it does not list are refused, so a future arm that forgets the message fails rather than drifting. Anything matching on the old exact string will need to stop; the variant and its `extension` field are unchanged.

**The CMYK refusal was factually wrong about the crate.** It said colour management is `crate::colour`'s job, "so the decoder has no CMS compiled into it and nothing else in the crate holds a black channel". The second half is flatly false: `crate::colour` has `Interpretation::Cmyk`, the libvips no-lcms ink model in both directions, and profiled CMYK through `icc_import`. The first half is the wrong shape: `jxl-oxide` takes a `ColorManagementSystem` at **runtime** through `JxlImage::set_cms`, and this build simply hands it none, so `jxl-render`'s default `jxl_color::NullCms` refuses every ICC transform (`jxl-color-0.11.0/src/cms.rs:47-57`, installed at `jxl-render-0.12.4/src/lib.rs:184`; jxl-oxide's own `lcms2` and `moxcms` integrations are optional and both off here). The message now names which of the two routes is missing, and the module docs cite the lines, so it reads as the wiring gap it is rather than a capability the crate lacks.

### About the red Integration Tests check

It was real and it was this PR's fault, and it is not what it looks like. The job clones libviprs-tests at a branch matching this one and falls back to `main`, and at the time of that run no matching branch existed, so it compiled `main`'s cell, which still called `encode_jxl(false)` against the signature this PR moved. A `feat/500-jxl` mirror branch now exists there at #159's commit, so the job resolves to a cell that compiles. The gate does not change that: the job only compiles the ported cells, it never runs them, and `encode_jxl`'s signature is the same under both cfgs.

## Not changed

- **Animated load.** #621, blocked on the page model in #564. This lane loads frame 0 and sets `n-pages`, which is byte-for-byte what a default `vips jxlload` does.
- **Metadata on save.** The encoder writes no box container, so there is nothing to write it into. Worth a follow-up issue if `--keep all` parity ever matters: a hand-built ISOBMFF wrapper could carry `Exif` and `xml ` boxes, though never an ICC profile, which lives inside the codestream.
- **`--features jxl` on this repo's own `integration-test` job.** That job compiles libviprs-tests' ported cells against this ref, and it cannot name the feature until libviprs-tests carries one, which is libviprs/libviprs-tests#160. Adding it now would only turn the check red against the mirror branch it actually resolves to. It is one line once #160 lands, and until then the cells are covered under the feature by that repo's own `run_ported_cells.sh` and `Feature Cell (jxl)` matrix entry.
- **`zune-jpegxl`'s `effort` knob** is left at the crate default on purpose. It is not `jxlsave`'s speed tier but a sampling radius for the prefix-code histograms, so it moves the compressed size and never the decoded pixels. Mapping `--effort 7` onto it would be a lie about what the number means.
