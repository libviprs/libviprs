Integer-precision convolution was dividing by the wrong number, and for some
masks by a number of the wrong sign. This makes it divide by `rint()` of the
scale on the mask the caller passed, which is what `vips_convi_gen` does, and
it makes the `f64` widening buffer underneath every fallible convolution
report an allocation failure instead of aborting the process.

Closes #547.

The second commit is the review round. It retires the divergence note that
still described the bug the first commit fixed, bounds `compass`'s `times` the
way libvips bounds it, and closes the one hole left in the abort-free claim.

#575 stays open on purpose. Its item 1 (`from_op_output`) landed in #598 and
its item 2 (the abort) is here; item 3 is per-row streaming, which removes the
8x widening rather than making it fallible, and that is a perf lane of its own.
It is also now the ceiling on the 8-bit arm.

## What was wrong (#547)

`vips_convi_gen` reads the scale and the offset off `convolution->M`, the mask
the caller handed in (`convolution/convi.c:757-760` at
`v8.18.0-95-gfe420cf3a`):

```c
VipsImage *M = convolution->M;
int scale = rint(vips_image_get_scale(M));
int rounding = scale / 2;
int offset = rint(vips_image_get_offset(M));
```

`vips_convi_build` does shadow `M` with the intized copy, but only for as long
as it takes to harvest the integer coefficients (`convi.c:1179-1181`), and it
never writes that copy back onto the object. So the brightness nudge
`vips__image_intize` computes into `out_scale` is dead code for `convi`. It is
live only for `conva` and `convasep` (`conva.c:1269`, `convasep.c:862`), the
approximate paths this crate does not implement.

libviprs threaded the nudge into the division, which is a different operation.
For the offset the two agree, because `rint()` is idempotent. For the scale
they do not, and the gap is not a rounding nit: on
`Kernel { data: [[3.0, 0.4, 0.4, 0.4, 0.4]], scale: 1.0 }` the nudge is `-1`,
so the sign of the divisor flips.

Measured on the 5x1 `Gray8` field of 100s from the issue:

```
vips 8.18.4, both arms  ->  255 255 255 255 255
libviprs before         ->    0   0   0   0   0
libviprs after          ->  255 255 255 255 255
```

Black where the reference is white, out of a mask any caller can build from
the public two-field `Kernel`.

## The oracle sweep, and which pins moved

None of them. That is the headline, and it is the reason the bug survived.

126 fractional masks (1x3, 3x3, 5x1, 5x3, coefficients to 0.1 in `-4..4`,
scales to 0.1 in `0.2..6.0`) over four fixtures: flat 5x1 uchar, 8x8 uchar
noise, 8x8 ushort noise, 8x8 float noise. Compared against
`VIPS_NOVECTOR=1 vips conv --precision integer`, the scalar `vips_convi_gen`
arm this module ports, per #558. Every case was also run with
`env -u VIPS_NOVECTOR`, unset rather than blanked, because an empty
`VIPS_NOVECTOR=` still counts as set.

```
before   191 / 504 outputs disagree with vips, across 33 distinct scales
         from 0.3 to 6.0
after     30 / 504 disagree, ALL of them |scale| < 0.5
```

The two vips arms disagreed with *each other* on 145 of the 252 uchar cases
(the ushort and float fixtures never reach the vector path, `convi.c:1151`
gates it on `VIPS_FORMAT_UCHAR`). That is ordinary #558 noise, and it is why
the comparison is against `VIPS_NOVECTOR=1` and not the default.

Not one existing pinned value moved. Every kernel in
`oracle-captures/convolution/capture.py` (`sharp`, `blur`, `line`, `sobelk`,
`box5`, `asym`, `box5_1d`, `hostile`) has integer coefficients over an integer
scale, and so does every `gaussmat`/`logmat` mask at integer precision (the
elements are `rint(20 * v)`, the scale is their sum) and every `edge.c` /
`canny.c` mask. For all of those the nudge is arithmetically a no-op:
`double_result == int_result == 1`, so `rint(scale + 0) == rint(scale)`. The
bug needs a mask whose coefficients do *not* round to themselves, which is
exactly what the public `Kernel` accepts and what nothing in the corpus passed.
`sharpen` was already right for a different reason: it computes its divisor as
`rint(mask.scale)` by hand.

The whole test-count delta is the three new tests.

The external suite cannot move either, and I checked rather than assumed:
`libviprs-tests/tests/ported_convolution.rs` builds `sharp` (scale 8), `blur`
(9), `line` (1) and `sobel` (1), all integer over integer, and every mask
`cli_convolution_diff.rs` hands to `conv`, `convsep` or `compass` is one of
`blur.mat` (scale 9), `sobel.mat` (1), `sep.mat` (10) or `hostile.mat` (3),
again all integer. The float `gaussmat`/`logmat` matrices in that suite are
inputs to the *mask creators*, never to an integer-precision convolution.

## The deliberate divergence

A mask scale below 0.5 leaves `int scale` at `0` and `vips_convi_gen` divides
by it. Measured on 8.18.4 with `[[1.0, 1.0]]` at scale 0.4, 0.49 and -0.4:

```
uchar   -> 0 0 0 0 0
ushort  -> 0 0 0 0 0
float   -> inf inf inf inf inf
```

Integer division by zero is undefined in C. This aarch64 build's `sdiv`
answers zero rather than trapping, and x86 would trap; the float-input arm
promotes the `int 0` to a double and prints `inf`. None of those three is
parity to pin.

`vips__image_intize` writes exactly this guard for its own copy at
`convi.c:895-897`, so the generator forgetting it is an oversight rather than a
design. libviprs takes the same guard and divides by 1, which is the only total
answer on offer, and pins it in
`conv_integer_scale_rounding_to_zero_divides_by_one` so it cannot drift. All 30
of the surviving sweep disagreements are this corner.

That is a fourth libvips defect for this epic, after the integer-conv vector
path, the wrong `atan2` comment in `canny.c:225-229` and `radload` never
parsing `FORMAT=`. It is written up in `ORACLE_FACTS.md` in bug-report shape.

## The abort (#575 item 2)

`samples_f64` widened every sample to `f64` with a plain `.collect()`. That
allocation is infallible: on failure it reaches `handle_alloc_error` and kills
the process. `try_conv`, `try_sobel`, `try_spcor` and every other fallible
entry point in the module sit on top of it, so none of them could report the
failure and no caller could catch it. A `Result` that does not cover
allocation is worse than no `Result`, because callers reasonably assume it
does, and the crate had already settled the question the other way one function
away: `raster.rs::alloc_op_output` reserves with `try_reserve_exact` and
returns `RasterError::AllocationFailed`, documented as never an abort.

It is the allocation most likely to be the one that fails. On a 4000x4000
`Rgb8` at integer precision it is 384 MB of a 486 MB peak, for 48 MB of input.

The widening now reserves through a small `try_buffer` helper with the same
contract as `alloc_op_output`, and so do the other image-sized intermediates in
the same functions: the two combine buffers in `compass` and the output planes
in `spcor` and `fastcor`, whose `# Errors` sections already promised
`ConvolutionError::Raster` and could not deliver it, plus the polar buffers in
`canny`. That is four extra one-line call sites; without them the fix would
have been cosmetic for three of the entry points it claims to cover.

`try_conv`, `try_convsep`, `try_compass`, `try_gaussblur`, `try_spcor`,
`try_fastcor`, `try_sobel`, `try_scharr` and `try_prewitt` are abort-free end
to end now, and `try_canny` is on its uchar arm. `try_gaussblur` took a second
pass to make that true; see the review round below.

## The review round

Three findings, all of them fair.

### The module still documented the bug this fixes

`src/convolution.rs` carries a `# Divergence from stock libvips` section, and
its `#547` bullet said libviprs "divides by the nudged scale", which is exactly
the behaviour the first commit removed. What gives it away is not how the prose
reads, because it reads fine in isolation: it is that the bullet was
byte-identical on `origin/main` and on the PR head. A change of behaviour that
leaves its own divergence note untouched has almost certainly left it
describing the old behaviour, because the note was written to describe the bug.

That bullet is gone. What stands in its place is the divergence this PR
actually creates, the mask scale that rounds to zero, and the contract for it
now sits on `Precision::Integer` beside the #558 parity contract instead of
only in the doc comment of the private `intize` helper, where no caller would
ever have found it. `intize` keeps one line and points at the public one. The
module header's lead-in changed with it: the two gaps are no longer "neither is
fixed here", and the second one is scoped to `conv`, `convsep` and `compass`,
the only three that convolve with a mask the caller wrote, since every mask
this module generates for itself carries an integer scale.

### `compass` took an unbounded `times`

`try_compass` checked `times` against zero and nothing else. It is a `u32` on
this surface, so `u32::MAX` reserved a result vector of 4.29 billion rasters,
on the order of 400 GB of address space, and then entered that many whole-image
convolutions: no error, no ceiling, nothing back inside half a minute.

libvips declares the bound on the property
(`VIPS_ARG_INT(class, "times", 101, ..., 1, 1000, 2)`,
`convolution/compass.c:162-167`). Measured on 8.18.4 with a 3x3 ones mask over
a 4x4 black image:

```
--times 1        runs
--times 1000     runs
--times 0        GLib-GObject-CRITICAL: value "0" of type 'gint' is invalid
                 or out of range for property 'times' of type 'gint'
--times 1001     same
--times 100000   same
```

Worth being exact about what that means, because the obvious reading is wrong:
the CLI does **not** exit. It prints the CRITICAL, leaves `times` at the
property default of 2, and writes an output. So the number the caller asked for
never reaches a convolution in vips, which is the property libviprs needs to
match, and it matches it with a typed refusal rather than a silent fallback.

`ConvolutionError::TimesOutOfRange { times, min, max }` replaces
`ConvolutionError::ZeroTimes` and covers both ends at once. `ZeroTimes` has
never been in a release and `ConvolutionError` is `#[non_exhaustive]`, so
nothing downstream can be matching on it. The variant is shaped after
`ConversionError::AcrossOutOfRange` from #612, which is the same finding one
module over on `arrayjoin`, down to the message and the three named fields.
Boundary tests pin 1 and 1000 accepted and 0, 1001, 100000 and `u32::MAX`
refused, and the bound is restated on the panicking `compass` as well as in
`try_compass`'s `# Errors`.

### The abort-free claim had one unnamed exception

The claim named `try_gaussblur`, and `try_gaussblur` was not abort-free. Its
`sigma < 0.2` branch is `vips_gaussblur`'s short circuit and it returned
`Ok(self.clone())`: a whole-image allocation that reaches `handle_alloc_error`
and ends the process. It is the one branch of the operation that touches no
other allocator, so it was the entire gap, and `try_canny` inherited it,
because `canny_gradient` blurs through `try_gaussblur` before it does anything
else.

`Raster::try_clone` closes it: a crate-internal fallible `Clone` that reserves
with `try_reserve_exact` and reports `RasterError::AllocationFailed`, carrying
the interpretation, the resolution and every attached field exactly as the
derived `Clone` does. No budget is applied, because the source raster is
already in memory and already passed whatever budget built it; the fallibility
is against the allocator, not against a declared size. Rebuilding through
`Raster::new` over a fresh buffer would have compiled and silently dropped all
that metadata, so both new tests check the header and the attachments rather
than only the pixels.

## Not changed, and what I found on the way

`try_sharpen` and canny's float arm still have infallible image-sized
allocations. I narrowed the claim rather than widening the fix, and the
CHANGELOG now names both exclusions so the claim cannot be read wider than it
goes. Both widen through `Raster::f32_samples`, a `pub fn ... -> Option<Vec<f32>>`
built on `.collect()`, so making them fallible is a public signature change,
and `sharpen` piles more on top of that: a `Vec<i32>` for the L plane, a clone
of the sample vector, a clone of the whole LabS raster, two
`vec![0i32; src.len()]` passes in `convsep_short_pass`, and the LabS round trip
through `colour.rs`, where every intermediate is a plain `vec![]`. Neither is
one allocation away from the list, so pretending otherwise would be the same
failure as a `try_` API that aborts. That is a `raster.rs` signature change
plus a `sharpen` rework, and it wants its own issue rather than being smuggled
in here.

#575 item 1 was already done by #598: `raster_from_f64`, `raster_from_i64`
and `edge_detect` all go through `alloc_op_output` / `Raster::from_op_output`
on `main` today.

I did not regenerate `oracle-captures/convolution/oracle.json`. It has no
fractional-coefficient kernel at all, which is precisely why it could not see
this, so it is worth adding one, but re-running `capture.py` rewrites 238 KB of
JSON and 56 KB of `commands.sh` in one go and that is not a diff to land in the
middle of a review batch. The measurements are in `ORACLE_FACTS.md` instead,
with the sweep harness beside them, and the discriminating cases are pinned as
test constants.
